# 프로젝트 예정 매입과 실제 지급

- `ProjectAmount.amount`와 `projects.cost`는 예정 매입을 유지한다. 지급 기록은 기존 금액을 덮어쓰지 않는다.
- `ProjectCostPayment`는 매입 건별 실제 지급액·지급일(YYYY-MM-DD)·메모·입력/최종 수정자를 저장한다. 여러 건의 부분 지급과 수정·삭제를 지원한다.
- `오늘 지급 완료` 체크는 별도 저장 버튼 없이 즉시 기록한다. 서버 한국시간 날짜와 `예정액 − 기존 지급 합계`의 양수 잔액만 사용하며, 이미 정산 완료되었거나 잔액이 0원이면 지급을 중복 생성하지 않는다. 지급 취소/수정은 상세 기록에서 명시적으로 처리한다.
- 실제 지급 합계 = 지급 기록 합계. 미지급 = 건별 max(예정 매입 − 지급액, 0)의 합. 정산 완료한 건은 잔액 0원이며 예정 대비 절감/초과를 표시한다.
- `예정액 지급`은 지급액이 예정액 이상이라는 뜻이다. 추가 지급 없음은 `정산 완료`로 별도 확정한다. 지급 기록 삭제 시 정산 완료는 해제된다.
- 예상 영업/당기순이익 계산식은 기존 정책을 유지한다. `실제 지출 기준 차액`은 매출 합계 − 실제 지급액이며 매출 미수금·미지급 비용을 반영하지 않은 참고값이다. 확정 순이익이나 현금잔고가 아니다.
- 프로젝트 열람 권한이 있는 활성 내부 관리자·팀장·사원(legacy user 포함)은 지급 기록을 편집할 수 있다. 예정 매입의 편집 권한과 매출 날짜의 본인 계정 제한은 기존 정책 그대로다.
- 외부 파트너/거래처/호스트 및 외부 연결이 붙은 계정은 지급 액션을 직접 호출해도 거부한다. 프로젝트 상세는 연결 범위의 이름·상태·일정·진행률만 SELECT한다.
- 지급 테이블은 RLS 기본 거부 정책을 적용한다. Prisma 런타임은 migration 소유자와 같은 서버 DB 계정을 사용하며, 브라우저/REST의 비소유자 역할에는 지급 행을 공개하지 않는다.
- 지급 저장은 프로젝트 advisory lock 및 매입 행 FOR UPDATE로 직렬화한다. 재시도 시 동일 지급 ID를 upsert하여 중복 금액을 막는다.
- 지급 기록이 있는 매입은 삭제·매출 전환 불가. 견적서 삭제/재분석 시 지급 기록이 있는 금액은 보존한다. DB FK도 지급 기록의 연쇄 삭제를 차단한다.
- 기존 매입에 지급 내역을 자동 생성하지 않는다. 다른 페이지의 기존 회사 장부/월별 매입은 예정 금액 기준이며 이번 지급액으로 대체되지 않는다.

## 배포

운영 적용에는 `20261103020000_add_project_cost_payments` migration이 필요하다. 새 테이블과 기본 false인 정산 필드만 추가하며 기존 재무 금액은 수정하지 않는다. 사용자 배포 승인 전에는 운영 migration/push/배포를 실행하지 않는다.

## 실제 PostgreSQL 검증

`src/__tests__/projectCostPayments.integration.test.ts`는 독립 PostgreSQL의 `erp_cost_test` DB에서만 실행된다. `ERP_COST_DB_TEST=1`과 `DATABASE_URL`의 host=127.0.0.1, port=55433, database=erp_cost_test 조건을 모두 요구한다. 그 외 실행에서는 skip 또는 거부한다. 실제 저장·독립 연결 재조회·동일 ID 중복 동시 요청·서로 다른 지급 동시 저장·잠금 대기·삭제/구분 전환 경쟁·지급 기록 보존·외부 계정 수정 거부·외부 최소 조회/연결 범위를 검사한다. 검증용 레코드는 테스트가 생성한 고유 ID 범위에서만 정리한다.

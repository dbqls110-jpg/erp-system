# 새 문의 이메일 알림

## 범위

- 수신자와 발신 계정은 `dbqls110@gmail.com`으로 고정한다.
- 기존 문의 탭의 고객 문의 / 공간 등록 / 공간 대관을 감지한다. VenueDA 관리자 상담 메신저의 새 메시지와는 별도 경로다.
- 메일에는 문의 종류와 로그인해야 열리는 고정 ERP 링크만 포함한다. 이름·연락처·문의 본문·첨부파일·금액은 넣지 않는다.
- 본인 계정만 연결·재개·중지할 수 있다. 박석영 팀장의 문의 조회 권한은 유지하되 메일 발신 설정 권한은 주지 않는다.
- 문의 읽음과 이메일 발송 이력은 분리한다. 메일을 보내거나 열어도 문의 읽음 숫자를 바꾸지 않는다.

## 연결

1. 검증 및 운영 배포 승인 후 migration과 코드를 적용한다.
2. 본인 계정으로 ERP 문의 페이지에서 `Gmail 연결`을 누른다.
3. Google에서 본인 계정으로 발송 권한에 직접 동의한다. 요청 범위는 `openid`, `email`, `gmail.send`이다. 받은메일 읽기·삭제 권한은 요청하지 않는다.
4. 기존 OAuth 클라이언트에 이미 등록된 `/api/admin/drive-callback`을 재사용하되, 이메일용 상태·쿠키가 있으면 별도의 검증/저장 경로로 분기한다. Drive 토큰은 교체하지 않는다.
5. Google 프로젝트에 Gmail API가 사용 설정되어 있어야 한다. API/권한 오류 시 프로젝트의 Gmail API 설정을 확인한다. Drive 앱 권한을 제거하여 해결하지 않는다.
6. 최초 연결 또는 알림 재개 시 기존 문의 전체를 발송 기준으로 저장하고, 본인에게 시험 메일 1건을 보낸다. 시험 발송이 성공해야 켜짐으로 표시한다.
7. 이후 추가된 문의만 신규 메일로 보낸다. Google OAuth 앱이 테스트 상태이면 refresh token이 만료될 수 있으므로 해당 프로젝트의 게시/검증 상태도 확인해야 한다.

토큰 원문은 채팅·문서·로그에 출력하지 않는다. `DRIVE_TOKEN_ENC_KEY`(기존 암호화 도구)를 사용해 이메일 전용 테이블에 암호화한다. 기존 Drive 토큰 레코드를 삭제하거나 덮어쓰지 않는다.

## 클라우드 실행

- `.github/workflows/inquiry-email.yml`이 약 5분 간격으로 전용 ERP endpoint를 호출한다. 회사 PC나 브라우저에 의존하지 않는다.
- 기존 GitHub 비공개 Secret `ERP_MAINTENANCE_SECRET`과 변수 `ERP_MAINTENANCE_ENABLED=true`를 재사용한다. 비밀값을 읽거나 새 키를 만들 필요가 없다.
- 최초 운영 배포와 Gmail 시험 발송이 성공한 뒤에만 GitHub 비밀값이 아닌 변수 `INQUIRY_EMAIL_ENABLED=true`를 설정한다. 이 변수가 없으면 스케줄 작업은 실행되지 않는다. 배포 중 구 버전 서버를 호출하거나 Gmail 연결 전부터 불필요한 확인을 반복하지 않도록 하는 활성화 장치다.
- 기존 DOT/업로드 복구 workflow의 실행 빈도와 코드는 변경하지 않는다.
- 활성화 전에는 원본 Sheets를 읽거나 메일을 보내지 않는다. 켜진 상태에서만 세 원본 목록을 조회한다. 시간당 최대 12회의 주기적 확인이며, 실행 지연에 따라 실제 횟수는 줄어들 수 있다.
- 현재 저장소는 공개 저장소이고 표준 Ubuntu 실행기를 사용한다. 현재 GitHub 정책상 표준 공개 저장소 Actions 실행은 무료다. 저장소를 비공개로 변경하거나 실행기 종류를 바꾸면 비용을 다시 검토한다. 기존 Render/DB/Google 서비스 한도는 별개다.
- GitHub 스케줄은 정시 실행을 보장하지 않으며 지연/누락 또는 공개 저장소 비활동으로 자동 중단될 수 있다. 즉시 알림 및 강한 운영 보장이 필요하면 문의 저장 측의 인증된 webhook + 별도 보장된 scheduler로 전환해야 한다.

## 중복·실패 처리

- 정렬/행 이동에 영향받지 않는 문의별 해시 키와 DB 복합 PK를 사용한다.
- 최초 기준 저장이 실패하면 초기화 완료로 간주하지 않는다. 목록 조회 오류를 빈 목록으로 바꾸지 않는다.
- DB 임대와 조건부 갱신으로 동시 작업을 하나로 제한한다. 한 실행에서 최대 5건을 처리하고 나머지는 다음 실행에 남긴다.
- Gmail 전송 자체의 자동 HTTP 재시도는 끈다. 인증 갱신 단계와 전송 단계에 시간 제한을 적용한다.
- 명확한 rate-limit 거절이나 발송 전 토큰 서버의 일시 장애는 10분 뒤 최대 5회까지 재시도한다. 인증/권한 실패는 알림을 중지하고 설정에 표시한다.
- Gmail API에는 메일 발송 멱등성 키가 없다. 응답 유실·5xx·시간초과 또는 오래된 `sending`은 `uncertain`에 남기며 자동 재발송하지 않는다. 전송 확인이 필요한 건수는 본인의 설정 화면에 표시한다.
- 실제 발송 성공 여부를 DB에 저장하지 못해도 해당 행을 다시 `pending`으로 되돌리지 않는다. 무조건 재시도해 중복 메일을 보내는 방식은 사용하지 않는다.
- 설정 중지와 동시 실행이 겹치면 중지된 설정을 이전 활성화 작업이 다시 켜지 못한다. 이미 전송 중인 1건은 회수할 수 없다.

## 운영 확인

1. Gmail 연결 후 본인에게 연결 점검 메일이 실제 도착하고 설정이 `켜짐`인지 확인한다.
2. 승인된 본인 문의 1건을 홈페이지에서 작성한다. 실제 고객/호스트에게 시험 답변은 보내지 않는다.
3. GitHub Actions에서 `Inquiry email notifications`를 수동 실행하여 HTTP 200과 성공을 확인한다.
4. 본인 받은편지함에서 새 문의 메일 1건을 확인한다. 재실행 후 중복 발송이 없는지 확인한다.
5. ERP 문의를 읽거나 메일을 읽은 상태와 무관하게 새 문의만 발송되고 읽음 카운터는 독립적으로 유지되는지 확인한다.

실제 Gmail 발송/클라우드 실행 검증 전에는 ‘이메일 연동 완료’로 보고하지 않는다.
